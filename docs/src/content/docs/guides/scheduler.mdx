The `condatainer run` command allows you to submit scripts as jobs to HPC cluster's scheduler. This guide covers how to request resources, pass arguments, execute job arrays over multiple inputs, and chain dependent jobs together.

## Understanding the Scheduler

If you're new to high-performance computing (HPC), here's a quick overview of how a cluster works:

- **Login Node**: The shared machine you connect to initially. It's meant for lightweight tasks like submitting jobs and managing files, not for running heavy analysis.
- **Compute Nodes**: The dedicated machines where your actual work runs.
- **Scheduler**: The software (like Slurm, PBS, or LSF) that manages the compute nodes, deciding when and where each job should run based on available resources.
- **Job**: A script packaged with a specific set of required resources. You submit the job, the scheduler queues it, and it begins executing once the resources are free.
- **Directives**: Instructions that tell the scheduler what resources your job needs, commonly as special script comments.

Here is an example of a script requesting 4 CPUs, 8 GB of memory, and 1 hour:

<Tabs syncKey="scheduler">
  <TabItem label="Slurm">
    ```bash
    #SBATCH --cpus-per-task=4
    #SBATCH --mem=8G
    #SBATCH --time=1:00:00
    ```
  </TabItem>
  <TabItem label="PBS">
    ```bash
    #PBS -l select=1:ncpus=4:mem=8gb
    #PBS -l walltime=1:00:00
    ```
  </TabItem>
  <TabItem label="LSF">
    ```bash
    #BSUB -n 4
    #BSUB -R "span[hosts=1] rusage[mem=2048]"
    #BSUB -W 1:00
    ```
  </TabItem>
  <TabItem label="CondaTainer">
    ```bash
    #NCPU: 4
    #MEM: 8G
    #TIME: 1h
    ```
  </TabItem>
</Tabs>

When you execute `condatainer run`, CondaTainer parses these directives and headers.

- If a scheduler is detected, it submits the script as a job and prints the resulting job ID.
- If no scheduler is found, or the script has no scheduler directive and no resource or job header, it executes the script immediately on the current machine.

**NOTE:** This page assumes jobs with one rank. If you are looking for MPI, check the [MPI](../advanced/mpi.mdx) page.

## Overriding Resources

While resources are typically defined inside the script via headers or directives, you can easily override them for a specific run using command-line flags:

```bash
condatainer run -c 8 -m 32G -t 4h analysis.sh
condatainer run -g a100:2 gpu_job.sh
```

- A flag replaces the value in the script for this run only.
- What neither the script nor a flag sets comes from the `scheduler.ncpu`, `scheduler.mem` and `scheduler.time` [settings](config.md) unless you changed them.
- Inside a job, it already has resources. `-c`, `-m`, `-t` and `-g` are ignored with a warning.

### Important Resource Flags

Each scheduler uses different directive syntax, but `condatainer run` standardizes the command-line flags across all of them:

<Tabs syncKey="scheduler">
  <TabItem label="Slurm">
    | Resource | Directive | `run` flag |
    |---|---|---|
    | CPUs | `#SBATCH --cpus-per-task=4` | `-c 4` |
    | Memory | `#SBATCH --mem=8G` | `-m 8G` |
    | Time | `#SBATCH --time=1:00:00` | `-t 1h` |
    | GPUs | `#SBATCH --gpus-per-node=a100:2` | `-g a100:2` |
    | Partition | `#SBATCH --partition=gpu` | `-p gpu` |
    | Account | `#SBATCH --account=lab` | `-A lab` |
    | Job name | `#SBATCH --job-name=quant` | `-n quant` |
    | Stdout | `#SBATCH --output=quant.log` | `-o quant.log` |
    | Stderr | `#SBATCH --error=quant.err` | `-e quant.err` |
  </TabItem>
  <TabItem label="PBS">
    | Resource | Directive | `run` flag |
    |---|---|---|
    | CPUs, memory, GPUs | `#PBS -l select=1:ncpus=4:mem=8gb:ngpus=2` | `-c 4`, `-m 8G`, `-g 2` |
    | Time | `#PBS -l walltime=1:00:00` | `-t 1h` |
    | Queue | `#PBS -q gpu` | `-p gpu` |
    | Account | `#PBS -A lab` | `-A lab` |
    | Job name | `#PBS -N quant` | `-n quant` |
    | Stdout | `#PBS -o quant.log` | `-o quant.log` |
    | Stderr | `#PBS -e quant.err` | `-e quant.err` |

    CondaTainer sends PBS only the GPU count, so a GPU model in `-g` is ignored. A `select` resource that CondaTainer does not recognize, such as `gpu_id=gpu0`, is kept.
  </TabItem>
  <TabItem label="LSF">
    | Resource | Directive | `run` flag |
    |---|---|---|
    | CPUs | `#BSUB -n 4` | `-c 4` |
    | Memory | `#BSUB -R "span[hosts=1] rusage[mem=2048]"` | `-m 8G` |
    | Time | `#BSUB -W 1:00` | `-t 1h` |
    | GPUs | `#BSUB -gpu "num=2:gmodel=a100"` | `-g a100:2` |
    | Queue | `#BSUB -q gpu` | `-p gpu` |
    | Project | `#BSUB -P lab` | `-A lab` |
    | Job name | `#BSUB -J quant` | `-n quant` |
    | Stdout | `#BSUB -o quant.log` | `-o quant.log` |
    | Stderr | `#BSUB -e quant.err` | `-e quant.err` |

    `span[hosts=1]` keeps all the cores on one node. Without it, LSF can spread them.
  </TabItem>
  <TabItem label="CondaTainer">
    | Resource | Header | `run` flag |
    |---|---|---|
    | CPUs | `#NCPU: 4` | `-c 4` |
    | Memory | `#MEM: 8G` | `-m 8G` |
    | Time | `#TIME: 1h` | `-t 1h` |
    | GPUs | `#GPU: a100:2` | `-g a100:2` |
    | Partition | `#PARTITION: gpu` | `-p gpu` |
    | Account | `#ACCOUNT: lab` | `-A lab` |
    | Job name | `#NAME: quant` | `-n quant` |
    | Stdout | `#OUTPUT: quant.log` | `-o quant.log` |
    | Stderr | `#ERROR: quant.err` | `-e quant.err` |

    - A bare `#MEM:` number is in GB, and a bare `#TIME:` number is in hours. `#TIME:` also reads `01:30:00`.
    - `#GPU:` takes a count (`2`), a type (`a100`) or both (`a100:2`). PBS ignores the type.
    - A relative `#OUTPUT:` or `#ERROR:` path starts from the directory you submit from.
    - Write the headers in the comment lines at the top of the script. If this cluster's scheduler directives in the same script set resources, the `#NCPU:`, `#MEM:`, `#TIME:` and `#GPU:` headers are ignored, and a warning names their lines.
  </TabItem>
</Tabs>

:::note
CondaTainer translates another scheduler's directives to this cluster's scheduler, such as `#SBATCH` lines on a PBS cluster. The partition and account are not translated.

The resources of a script come from the first of these that sets one:

1. This cluster's scheduler directives.
2. The CondaTainer headers, such as `#NCPU:`.
3. Another scheduler's directives.

- A directive that sets no resource, such as `#SBATCH --qos=high` or `#SBATCH --nodelist=node1`, is passed to the job as written. The headers still give the resources.
- The job name, the output and error paths, the partition and the account are read from both the directives and the headers. Setting the same one in both is refused, and the message names both lines.
:::

### Resources by overlay

A resource header can name a slot, so a script asks for more memory only when a larger overlay fills the slot. How to declare a slot and fill it with `--slot` is in [Swap an overlay with a slot](overlays.md#swap-an-overlay-with-a-slot).

```bash title="align.sh"
#!/bin/bash
#DEP: star/2.7.11b
#SLOT: star_index default=human choices=human=grch38/star/2.7.11b/gencode47-151,mouse=grcm39/star/2.7.11b/gencodeM36-151 env=STAR_INDEX_DIR
#NCPU: 8
#MEM: 40G
#MEM: 32G star_index=grcm39
#TIME: 4h
```

```bash
condatainer run --dry-run --slot star_index=mouse align.sh
```

The dry run prints the line each header used and why:

```text
Conditions:
  #MEM   32G  line 6, star_index matched grcm39
```

`#NCPU:`, `#MEM:`, `#TIME:` and `#GPU:` take `slot=value` after the value. The slot is checked against its overlay name, not its short name, so with `mouse=grcm39/star/...` write `star_index=grcm39`.

| Value | Matches |
|---|---|
| `star_index=grch38` | The overlay name, or the start of it by whole parts. `grch38/star/...` matches, `grch38_grcm39/star/...` does not. |
| `star_index=grch38,grcm39` | Any one entry of the list. |
| `star_index=regex:^grch38/` | A regular expression, used as written. It matches anywhere in the name unless it holds `^` or `$`. |

- A header with several slots needs all of them to match. A slot left unbound matches nothing.
- The first line that matches is used. The line with no slot is used when none does.
- When no line matches and none is without a slot, the script is refused. The message says what each slot is bound to.
- `-c`, `-m`, `-t` and `-g` replace the header they set, so that header needs no matching line. A script that also has `#SBATCH`, `#PBS` or `#BSUB` resource lines is refused.

#### With a slot group

Slots can share a [group](overlays.md#bind-several-slots-with-one-value), which one `--slot` value fills. A header can name the group:

```bash title="align.sh"
#SLOT: gtf group=species default=human choices=human=grch38/gtf/gencode/47,mouse=grcm39/gtf/gencode/M36
#SLOT: star_index group=species default=human choices=human=grch38/star/2.7.11b/gencode47-151,mouse=grcm39/star/2.7.11b/gencodeM36-151
#MEM: 40G
#MEM: 32G species=mouse
```

```bash
condatainer run --dry-run --slot species=mouse align.sh
```

- A group is checked against its short name, so write `species=mouse`.
- A group has a value only when all its slots are bound to choices with one short name.
- When a `strict=false` slot holds another overlay, as in `--slot gtf=my/custom --slot star_index=human`, a group condition matches nothing. Keep a line with no condition, or give `-m`.

### Standardized Environment Variables

When your script runs through `condatainer run`, these variables hold its resources:

| Variable | Value |
|---|---|
| `$NCPU` | CPUs allocated to the job |
| `$MEM` | Memory of the job in MB |
| `$MEM_GB` | Memory of the job in GB |
| `$OMP_NUM_THREADS` | The same as `$NCPU` unless it was already set |

- In a job they are the job's resources. Outside a job they come from the script, the flags and the settings above.
- When the job does not report its memory, `$MEM` is the script's `#MEM` or the `scheduler.mem` setting with a warning.

```bash
samtools sort -@ "$NCPU" -o sorted.bam input.bam
```

## Script Layout

A script starts with a first line that names the program that runs it. Next comes the header block, the comment lines that tell CondaTainer and the scheduler what the job needs. The commands follow.

<Tabs syncKey="script">
  <TabItem label="Bash">
    ```bash title="count.sh"
    #!/bin/bash
    #DEP: samtools/1.22

    #NCPU: 4

    samtools --version
    ```
  </TabItem>
  <TabItem label="Python">
    ```python title="count.py"
    #!/bin/env python3
    #DEP: samtools/1.22
    #DEP: python/3.12.13

    import subprocess
    subprocess.run(["samtools", "--version"])
    ```
  </TabItem>
  <TabItem label="R">
    ```r title="version.R"
    #!/bin/env Rscript
    #DEP: ubuntu24/r/4.4.3
    #DEP: ubuntu24/r-build-essential

    cat(R.version.string, "\n")
    ```
  </TabItem>
</Tabs>

- The first line is `#!/bin/bash`, or `#!/bin/env <program>` for another language, such as `python3` or `Rscript`. `#!/usr/bin/bash` and `#!/usr/bin/env` work too.
- Any other first line is refused, including `#!/bin/sh` and a script with none. The word after `env` must be a program, not an option such as `-S`.
- The program must exist inside the container, in the base image or in an overlay listed by `#DEP:`.
- A `#SLOT:` line is a `#DEP:` whose overlay can change when the script runs. See [Swap an overlay with a slot](overlays.md#swap-an-overlay-with-a-slot).
- The header block is the first line, the blank lines and the comment lines, up to the first line of code. Directives, such as `#SBATCH` and `#NCPU:`, after the first command are ignored.

## Run Execution Options

You can control exactly how `condatainer run` behaves using the following flags:

```bash
# Dry Run: Show what would happen without actually submitting or running anything
condatainer run --dry-run analysis.sh
```

Any values provided after the script name are passed directly into the script as positional arguments (`$1`, `$2`, etc.):

```bash
condatainer run sort.sh /data/raw/sample1.bam results/sample1/
```

## Job Arrays

A **job array** allows you to submit many similar jobs simultaneously. Each job in the array executes the same script but processes its own unique input. The scheduler manages them independently, allowing them to run concurrently across multiple compute nodes.

Instead of writing complex array logic in your script, you can use the `--array` flag. CondaTainer reads an input text file where each line represents a single job, and the words on that line are passed as arguments to the script:

```text title="samples.txt"
sample1 condition_A
sample2 condition_B
sample3 condition_C
```

When submitted, this file spawns three separate jobs:

| Job | Input Line | Argument `$1` | Argument `$2` |
|---|---|---|---|
| 1 | `sample1 condition_A` | `sample1` | `condition_A` |
| 2 | `sample2 condition_B` | `sample2` | `condition_B` |
| 3 | `sample3 condition_C` | `sample3` | `condition_C` |

- Every line must contain the same number of arguments. A quoted string counts as one.
- Blank lines are refused.

The script reads them as positional arguments `$1`, `$2`:

<Tabs syncKey="scheduler">
  <TabItem label="Slurm">
    ```bash title="quant.sh"
    #!/bin/bash
    #SBATCH --cpus-per-task=4
    #SBATCH --mem=8G
    #SBATCH --time=1:00:00

    #DEP: salmon/2.7.0
    #DEP: grch38/salmon/2.7.0/gencode47-k31

    # $1 is the sample, $2 the condition
    salmon quant -i "$SALMON_INDEX_DIR" -p "$NCPU" -l A \
      -r "reads/${1}.fq" -o "quants/${1}_${2}"
    ```
  </TabItem>
  <TabItem label="PBS">
    ```bash title="quant.sh"
    #!/bin/bash
    #PBS -l select=1:ncpus=4:mem=8gb
    #PBS -l walltime=1:00:00

    #DEP: salmon/2.7.0
    #DEP: grch38/salmon/2.7.0/gencode47-k31

    salmon quant -i "$SALMON_INDEX_DIR" -p "$NCPU" -l A \
      -r "reads/${1}.fq" -o "quants/${1}_${2}"
    ```
  </TabItem>
  <TabItem label="LSF">
    ```bash title="quant.sh"

    #BSUB -R "span[hosts=1] rusage[mem=2048]"
    #BSUB -W 1:00
    ```

### Running Arrays

```bash
# Submit the array
condatainer run --array samples.txt quant.sh

# Limit the array so a maximum of 4 jobs run concurrently
condatainer run --array samples.txt --array-limit 4 quant.sh   

# Preview the arguments for each job without submitting
condatainer run --dry-run --array samples.txt quant.sh         
```

- Any manual positional arguments provided on the command line will be appended **after** the array's line arguments.
- Arrays must be submitted to a scheduler. `--array` is refused when the run would not submit: no scheduler or inside a job.
- The script cannot contain its own array directive.

## Job Chaining (Dependencies)

**Job chaining** allows you to configure a job so that it waits for a previous job to finish before starting. This feature enables you to build multi-step pipelines directly from bash scripts, without needing complex workflow engines like Nextflow or Snakemake.

Because `run` strictly outputs the job ID to standard output, you can easily capture it in a variable and pass it to the next step:

```bash
JOB_ID=$(condatainer run step1.sh)
condatainer run --afterok "$JOB_ID" step2.sh
```

| Flag | Condition for the next job to start |
|---|---|
| `--afterok <ids>` | The previous jobs completed successfully without errors. |
| `--afternotok <ids>` | The previous jobs failed. |
| `--afterany <ids>` | The previous jobs finished, regardless of success or failure. |

- Give several IDs separated by colons: `--afterok 123:456`.
- With an array, the next job waits for every job in the array.

For example, a pipeline over every sample in `samples.txt`: trim, align and quantify each, then one job that collects the results:

```bash
TRIM=$(condatainer run --array samples.txt trim.sh)
ALIGN=$(condatainer run --array samples.txt --afterok "$TRIM" align.sh)
QUANT=$(condatainer run --array samples.txt --afterok "$ALIGN" quant.sh)
condatainer run --afterok "$QUANT" collect.sh samples.txt
```

### Submitting From Inside a Job

A job that plans a pipeline can submit the steps after it. Inside a job, `condatainer run` runs its script in that job. `--submit` makes it submit a new job instead, even from inside the job's container:

```bash
JOB=$(condatainer run --submit step1.sh)
condatainer run --submit --afterok "$JOB" step2.sh
```

- Inside a container, `--submit` goes through [`host-run`](host-run.md), so the job needs it. For jobs started by `condatainer run`, add `run` to the `host_run.launch` [setting](config.md).
- `--submit-on` picks the node the job is submitted from: `localhost`, `login` or a node name.

## Container Headers

Just as you use `#DEP:` to define overlays, these headers set `condatainer run` options inside the script:

```bash
#!/bin/bash
#DEP: bcftools/1.22
#BIND: /data:/data

bcftools view /data/input.vcf | head
```

| Header | Effect |
|---|---|
| `#BIND: HOST:CONTAINER` | Make a host directory available inside. Repeat the line for more. `$VAR` expands when the job starts. |
| `#WRITABLE:` | Mount `.img` overlays as writable. |
| `#FAKEROOT:` | Appear as root inside the container. |

- `#WRITABLE:` cannot be used with `--array` or with more than one rank, since only one process can write to an overlay.
- `#WRITABLE:` and `#FAKEROOT:` are switches. Write the line with nothing after the colon to turn the option on, and delete the line to turn it off. Writing a value other than `true` is an error.
- A `--bind` on the command line to the same container path replaces the script's `#BIND:`.
